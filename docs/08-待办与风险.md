| 9 | **移动端表现** | 在移动端 SiYuan 里粘贴代码 | 影响 `frontends` 声明 |

## 2. 风险登记

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| wasm 首次加载失败（网络/内核鉴权/CSP） | 中 | 必须有降级路径：直接跳到规则表；失败时 `showMessage` 提示一次并自动关闭 betlang 层 |
| 低端设备上 wasm 慢 | 低 | 采样上限 8 KB；必要时提供“低功耗模式”（只用规则表） |
| 误判导致用户数据被改 | 中 | 自动识别只处理空语言块；有明显代码特征时最低置信度为 `0.2`，否则提高到 `0.6`，并在写入前再次校验块状态 |
| 破坏撤销栈 | 中 | 用 `/api/transactions` 并附 `undoOperations`；不要直接改 DOM |
| 与 SiYuan 内部实现耦合（DOM 结构变化） | 中 | 尽量用 `data-type="NodeCodeBlock"` 与 `.protyle-action__language` 这两个稳定标识；把 DOM 访问集中在 `src/siyuan-dom.ts` 一个模块里，便于升级时改一处 |
| 引入 Rust 工具链增加维护成本 | 中 | 把 wasm 产物**签入仓库**（不要要求使用者装 Rust），只在发版时才重新构建；在 docs 里写清楚构建步骤 |
| 集市审核对 `.wasm` 资源的限制 | 中 | 提前确认集市是否允许二进制资源；`package.zip` 里带上 wasm 后体积是否超限 |
| betlang 上游停止维护 | 低 | 模型和代码都很小，可以 fork 后自持；也可退回规则表方案 |
| 纯列表 / 散文被误判成 YAML / Markdown | 中 | 只处理代码块；缺少明显代码特征时将最低置信度提高到 `0.6`，保留高置信声明式代码并过滤普通文本 |

## 3. 开放问题（需要产品决策）

### 3.0 已闭环的问题（不要再重新论证）

| 问题 | 结论 | 证据 |
|---|---|---|
| 用 `hljs.highlightAuto` 做长尾兜底会不会更好？ | **不会，明显更差** | 103 个真实长尾文件上准确率 14.6%（全量 201）/ 33.0%（去掉污染语法），关键词规则表 61.2% 且快 400 倍。见 `03-识别引擎选型.md` 第 8 节 |
| 用 Magika 换更广的覆盖率？ | **不换** | 实测 3.35–4.83 秒/次、模型 3.14 MB 且需联网，只多覆盖 20 种语言 |
| 需要 Rust 工具链吗？ | **需要，但只在发版时** | wasm 产物签入仓库，使用者不需要装 Rust |

### 3.1 可向上游反馈的问题（非本插件职责）

SiYuan 内置的 highlight.js 第三方语言包 `third-languages.js` 里的 `moonbit` 语法
会污染 `hljs.highlightAuto` 的结果（Rust/Python/Go 都会被判成 MoonBit），
连带影响任何使用自动检测的功能与插件。可作为 issue 反馈给 SiYuan。
证据与复现脚本：`scripts/moonbit-probe.cjs`。

1. 是否要支持“键入时自动识别”（Zed 的行为），还是只在粘贴时识别？
   —— 建议默认只在粘贴时识别，因为笔记场景里粘贴占绝大多数，且 on-type 的开销与误判风险更高。
2. 识别成功后要不要给用户一个提示（toast / 状态栏）？
   —— 建议默认静默，提供“撤销识别”的命令即可。
3. 已在文档里存在的无语言代码块，要不要在打开文档时批量识别？
   —— 建议不做（性能与风险都高），改为提供手动命令。
4. 要不要在语言下拉列表里加一个“自动识别”项作为显式触发入口？
   —— 推荐做（用 `code-language-update` 注入），成本低且能兜住“未识别”的场景。
5. 规则表要覆盖多少种长尾语言？
   —— 建议先做 15–25 条高频长尾（fortran / ada / pascal / matlab / graphql / protobuf / nginx / glsl / vim / wasm …），其余保持不识别。
