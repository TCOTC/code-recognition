# 03 识别引擎选型

## 1. 结论

**主力引擎用 betlang。** 理由：

1. 速度快 2 个数量级（唯一满足“速度要求高”的选项）；
2. 47 KB 模型编进二进制，完全离线，无运行时下载；
3. 48 个输出标签全部是源码语言，与“给代码块选语言”这个任务天然对齐；
4. 有 Zed 在生产环境验证过的策略层可以照抄（见 `02-Zed实现调研.md`）。

**但也必须清楚它的短板**：betlang 只覆盖 SiYuan 语言集里的 46 种（22.9%），
长尾语言要靠规则表兜底（见 `06-插件设计方案.md`）。

**不要用 Magika。** 见第 4 节的实测数据。

## 2. 三个候选方案

| | A. betlang | B. Magika（npm `magika`） | C. hljs `highlightAuto` |
|---|---|---|---|
| 形态 | Rust crate，需自己编 wasm | 现成 npm 包，JS + tfjs | SiYuan 里已经加载好了 |
| 模型体积 | 47,840 B | 3,138,239 B（+ 2,141 B config） | — |
| 模型来源 | 从 Magika `standard_v3_3` 蒸馏的学生模型 | `standard_v3_3` 本体 | — |
| 输出 | 48 个源码语言 + 校准概率 | 214 个内容类型（含二进制/文档） | 语言名 + relevance 分数 |
| 网络需求 | 无 | 需从 `google.github.io` 拉模型（可自托管） | 无 |
| 额外依赖 | 无（wasm 单文件） | `@tensorflow/tfjs`（百 MB 级 node_modules） | 无 |
| 本机实测单次耗时 | 原生 ~3ms【引用】/ wasm【待验证】 | **3.35–4.83 秒**（Node，tfjs 纯 JS CPU 后端） | 19.5 ms / 338 B；176.5 ms / 7 KB |
| 覆盖 SiYuan 的 201 种语言 | 46（22.9%） | 66（32.8%） | 201（100%） |

## 3. 为什么不是 C（hljs highlightAuto）

它覆盖 100% 且零依赖，看起来最省事，但有两个致命问题：

**其一，慢。**【实测】本机加载 SiYuan 自己的 `highlight.min.js`（201 语言）后计时：

```
highlightAuto(201 语言全量, 338B)     19.51 ms/次
highlightAuto(201 语言全量, 7KB)     176.52 ms/次
highlightAuto(限定 6 个候选, 338B)     0.43 ms/次
highlight(指定 rust)                   0.10 ms/次
```

全量是把 201 种语法各解析一遍，7 KB 就要 176 ms，长代码块会到几百毫秒。

**其二，不准。** 同一段 7 KB 的 Rust 代码，`highlightAuto` 的答案是 **moonbit**
（relevance 700）。relevance 打分的判别力在真实代码上并不可靠。

**可用法**：只在候选集已经收窄时使用（限定 6 个候选是 0.43 ms，比全量快 400 倍）。
把它当“通用兜底”的后果见第 8 节——实测只有 14.6%。

## 4. 为什么不是 B（Magika）

它确实覆盖更多语言（66 vs 46），但代价不成比例：

1. **慢到不可接受**：本机实测单次 3.35–4.83 秒。这个数字来自 Node 的 tfjs
   **纯 JS CPU 后端**，是同一台机器上 betlang 的约 1000 倍。Electron 渲染进程通常
   能用 WebGL（会快很多），但远程桌面 / 虚拟机 / 禁用 GPU / 软件渲染的环境会掉回 CPU 后端。
2. **体积**：模型 3.14 MB，比 betlang 大 66 倍，另加 tfjs 运行时。
3. **联网**：默认从 `https://google.github.io/magika/models/standard_v3_3/model.json`
   下载模型，与 SiYuan 离线优先的定位冲突（自托管可解决，但增加部署负担）。
4. **标签空间不适配**：214 个标签里包含 `png` / `pdf` / `pebin` / `randombytes`
   这类与代码语言无关的类型，浪费判别力，还要维护更大的映射表。
5. **只多覆盖 20 种语言**，剩下 127 种两者都覆盖不到，所以它并不能解决根本问题。

唯一值得肯定的差异：Magika 有 `_getOutputLabelFromModelPrediction` 里的
每标签置信度阈值和 `medium_confidence_threshold = 0.5`，低于阈值会**降级输出 `txt`**。
这在文件类型识别里是优点（宁可不说），在编辑器里是缺点（要的是尽力猜 + 调用方决定）。

## 5. 覆盖率实测（关键约束）

【实测】加载 SiYuan 的 hljs 得到 201 个语言名，与两个模型的标签空间取交集
（已做别名归一：`bash`→`shell`、`csharp`→`cs`、`dos`→`batch`、`h5`/`sgml`/`vue`→`html`、
`svg`→`xml`、repl 变体与 `plaintext` 忽略）：

```
hljs(SiYuan) languages = 201
Magika labels          = 214
betlang labels         =  48

hljs covered by betlang = 46 (22.9%)
hljs covered by Magika  = 66 (32.8%)
hljs covered by neither = 127
```

betlang 覆盖的 46 种（全部是高频语言）：

```
armasm bash c clojure cmake cpp csharp css dart dockerfile dos elixir erlang
go gradle groovy haskell ini java javascript json julia kotlin lisp lua markdown
objectivec ocaml perl php powershell python r ruby rust scala shell sql swift
typescript vbnet vbscript verilog x86asm xml yaml
```

Magika 比 betlang 多出来的 20 种：

```
autohotkey autoit awk coffeescript diff erb fortran handlebars latex makefile
matlab prolog protobuf scss smali solidity tcl twig vhdl wasm
```

两者都覆盖不到的 127 种：见 `appendix/数据附录.md`。
其中绝大多数是长尾语言（abap / ada / brainfuck / crystal / glsl / graphql / nginx /
protobuf / vim …），用关键词规则表兜底比用模型更划算。

## 6. 一个容易忽略的事实：betlang 就是 Magika 的学生

【源码】`magika@1.0.0` 的 `MODEL_VERSION = "standard_v3_3"`，
而 betlang 的模型卡明确写着它是从 **Google Magika v3.3 teacher** 蒸馏出来的。
所以这不是两个独立方案，而是同一血缘的教师/学生：

| 指标 | 值（betlang 模型卡） |
|---|---|
| 留出集文件级准确率 | `test_fs_accuracy = 0.942353` |
| macro recall | `macro_recall = 0.939690` |
| 与教师模型答案一致率 | `test_teacher_parity = 0.944055` |
| 评测集规模 | 34,087 个留出文件（48 类均衡） |

即：**用 1/66 的体积换到约 94% 的教师一致率**。这就是选它的根本理由。

## 7. 一个公平性提醒（别被单次实验误导）

我们在 betlang 自己的测试语料（48 个语言样本）上跑过 Magika，结果是
raw top-1 47/48（唯一真错的是 334 B 的 HTML 被降级成 `txt`），限制到 48 类子集里取 argmax 则 48/48。

**这批语料对 betlang 有利**（betlang 的 CI 就断言它在这批样本上全部命中），
所以这个数字**不能**当作准确率对比。可信的对比只有第 6 节的 34k 留出集数据。
详见 `07-实测数据与复现.md`。

## 8. 补充实测：`highlightAuto` 当兜底到底行不行

结论先行：**不行，比关键词规则表差得多**。下面是 2026-09-10 在本机做的对照实验。

### 8.1 语料

从本机真实项目里收集 **103 个文件、11 种长尾语言**（都是 betlang 覆盖不到的语言），
每文件只取前 1024 字节（模拟代码块场景）。真值由扩展名确定：

```
.proto→protobuf  .wat→wasm  .scss→scss  .tcl→tcl  .awk→awk  .diff→diff
.hbs→handlebars  .erb→erb   .vim→vim    .graphql→graphql  .coffee→coffeescript
```

样本来源：`C:\Users\Admin\go\pkg\mod`（1457 个 .proto、117 个 .wat）、
`D:\CodeProjects`、`C:\Users\Admin\.vscode\extensions`、`C:\Users\Admin\zed-src`。

脚本：`scripts/fallback-eval2.cjs`、`scripts/rule-vs-hljs.cjs`。

### 8.2 候选集规模对 `highlightAuto` 的影响

| 变体 | 候选集 | 准确率 | 平均耗时 |
|---|---|---|---|
| A | 全部 201 个语言 | **14.6%** | 37.5 ms |
| B | 155 个（betlang 覆盖不到的） | **15.5%** | 24.0 ms |
| C | 155 个去掉 2 个污染语法（moonbit、dns） | **33.0%** | 22.9 ms |
| D | 只留这 11 个真值语言（**作弊上限**） | **81.6%** | 1.5 ms |

逐语言明细（A 全量 / D 上限）：

```
protobuf  2/10 | 10/10      scss      1/10 | 10/10      diff      0/10 | 10/10
wasm      9/10 | 10/10      tcl       1/10 |  8/10      vim       2/6  |  6/6
awk       0/10 |  9/10      erb       0/10 |  5/10      graphql   0/7  |  2/7
handlebars 0/10 | 6/10      coffeescript 0/10 | 8/10
```

### 8.3 关键词规则表 vs `highlightAuto`（同一批文件）

| 方案 | 准确率 | 平均耗时 |
|---|---|---|
| 关键词规则表（11 种语言、约 40 条正则，现写现测） | **61.2%** | **0.094 ms** |
| `hljs.highlightAuto`（全量 201） | 14.6% | 37.7 ms |

规则表**准确率高 4 倍、速度快 400 倍**。而且规则表的弱项（scss 2/10、graphql 0/7、
handlebars 3/10、coffeescript 3/10）可以通过继续补特征改进，属于工程投入问题；
`highlightAuto` 的问题是结构性的（见 8.4），调不动。

### 8.4 根因诊断：relevance 在语言之间不可比

`scripts/moonbit-probe.cjs` 的输出：

```
===== 不含 third-languages.js（193 个语言） =====
纯英文散文   -> livecodeserver relevance=15   第二名=applescript(14)
Rust 代码    -> dns            relevance=25   第二名=rust(17)
Python 代码  -> dns            relevance=28   第二名=dart(22)
Go 代码      -> dns            relevance=22   第二名=go(21)

===== 含 third-languages.js（201 个语言，SiYuan 的实际状态） =====
纯英文散文   -> livecodeserver relevance=15   第二名=applescript(14)
Rust 代码    -> moonbit        relevance=35   第二名=dns(25)
Python 代码  -> moonbit        relevance=42   第二名=dns(28)
Go 代码      -> moonbit        relevance=27   第二名=dns(22)
moonbit 语法: keywords 数量=144
```

两个独立的污染源：

1. **`moonbit`**（由 SiYuan 的 `third-languages.js` 引入）声明了 144 个极泛用的关键字：
   `as / if / let / for / type / return / match / String / Array / Map / Option / Result / Error / hash …`。
   任何主流语言代码都会命中一堆，relevance 被堆到最高。语法自带的 `relevance: 1` 是
   **每次命中的加分系数，不是上限**，所以它挡不住累加。
2. **`dns`**（核心构建自带，是 ini 家族语法）对任何含 `=`、`:`、`#` 的文本都给高分。

结果是 **Rust / Python / Go 这些最主流的语言都会被判错**——问题不是“长尾不行”，
而是“整体不可靠”。这也解释了代码块里那段 7 KB Rust 为什么会被判成 moonbit。

（顺带说明：这只影响 `highlightAuto`，不影响指定语言的 `hljs.highlight(code, {language})`，
所以 SiYuan 的正常高亮功能不受影响。）

### 8.5 那么 `highlightAuto` 什么时候可用

它**只在候选集已经收窄时**可用——这也正是 highlight.js 官方文档的立场
（第二个参数 `languageSubset` 是给这种场景准备的）。变体 D 证明：
当候选压到十几个时，准确率能到 81.6%，耗时 1.5 ms。

但“已知候选集很小”恰恰意味着你不需要通用兜底。

另外有一个特例值得注意：`wasm`(.wat) 在 `highlightAuto` 上是 9/10，
比规则表（5/10）好——对语法特征极强的语言，它的专用语法确实更准。
所以**混合策略**（规则表为主，个别语言用 hljs 限定候选兜底）是可行的，但不是必需的复杂度。

## 9. 最终建议

```
第 1 层（主力，必做）：betlang + wasm        → 覆盖 46 种主流语言，毫秒级
第 2 层（兜底，建议做）：关键词/特征规则表    → 覆盖剩余长尾，微秒级
第 3 层（可选，谨慎）：hljs highlightAuto     → 仅当候选集已被收窄到十几个时才可考虑
```

**明确不要**把 `highlightAuto` 当通用兜底（第 8 节实测全量只有 14.6%，
而且会把 Rust/Python/Go 判成 MoonBit）。

不要引入 tfjs、不要引入 onnxruntime、不要引入超过 1 MB 的模型文件。
